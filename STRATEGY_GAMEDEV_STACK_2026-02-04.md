## 1) Роли документов (чтобы не разъехались)

Чтобы стратегия оставалась “стройной”, каждому документу нужна строгая роль:

1) **`WORKFLOW_GAME_CONCEPT_PLAN.md` — SSOT (single source of truth)**  
   Здесь фиксируются: сущности/статусы, core loop, ограничения GitHub Pages, UX‑точки, этапы, DoD и риски.  
   **Правило:** если решение влияет на продукт/архитектуру, оно должно быть отражено здесь.

2) **`ANALYSIS_AND_VISION_2026.md` — Vision + Epics (“почему/что/эффект”)**  
   Задаёт направление: вирусность, роли пользователей, Smart Onboarding, high‑level план действий.

3) **`FEATURE_PATH_CREATOR.md` — Feature Spec (“как выглядит фича”)**  
   Конкретизирует UGC‑ветку: как открывается, какие механики, какие триггеры, как превращается в контент и куда уходит на модерацию.

4) **`CODEX_ANALYSIS_2026-02-04.md` — Reality Check (“что уже правда в коде”)**  
   Это слой проверки: прогресс/профиль/избранное/экспорт/импорт уже реализованы; порты/стейджинг; где доки расходятся с реальностью.

Мини‑правило синхронизации:
- `ANALYSIS_AND_VISION_2026.md` задаёт **почему** и **какие эпики**,
- `WORKFLOW_GAME_CONCEPT_PLAN.md` фиксирует **как это устроено в системе**,
- `FEATURE_PATH_CREATOR.md` описывает **конкретный эпик‑модуль**,
- `CODEX_ANALYSIS_2026-02-04.md` фиксирует **факт‑состояние репы**.

## 2) Продуктовая логика = 3 взаимосвязанных игрового цикла (Loops)

Если собрать оба документа в одну “игровую” логику, получается не набор хотелок, а три цикла поведения:

### Loop A — Core Loop (“Маршрут развития”)
Категория → Значок → Уровень → Реальное действие → Рефлексия/пруф → Прогресс → Следующий шаг.

Что уже есть в коде (важно понимать, что фундамент сделан):
- `useUserProgress` + `ProgressContext` (localStorage),
- `ProfileView` (паспорт, ранги, маршруты, избранное, экспорт/импорт, “пруфы” через Telegram‑deeplink),
- отметка уровней + конфетти.

Критерий “качественного геймдева” в этом цикле: **игрок чувствует движение** даже без backend’а.

### Loop B — Social/Viral Loop (“Поделись моментом”)
Смысл: делимся не “таблицей прогресса”, а **моментом истории**.

В `ANALYSIS_AND_VISION_2026.md` это оформлено как:
- “ИИ‑Манифест Маршрута” (старт/избранное → карточка намерения),
- “Генератор Командных Мемов” (командная идентичность).

В `FEATURE_PATH_CREATOR.md` это оформлено как:
- “Карточка Созидателя” (предложение в канон → сторис/рилс‑карточка).

Общий продуктовый принцип: **каждому важному действию соответствует share‑артефакт** (Story 9:16 + Wide 16:9) и короткая подпись.

### Loop C — Creator Loop (“Создатель Пути” / UGC endgame)
Смысл: высшая ступень — не потреблять контент, а создавать его (соавторство методики).

`FEATURE_PATH_CREATOR.md` задаёт правильную конструкцию:
- “Мастерская” открывается не всем, а через каноничные значки `1.16.1` / `1.16.2`,
- предложить можно: новый значок / новую категорию / новый арт‑скин,
- всё уходит на модерацию (Telegram/чат вожатых), а игрок получает share‑карточку.

Почему это важно продуктово:
- UGC даёт “бесконечный контент” без бесконечной команды,
- усиливает open‑source философию,
- делает “Путеводитель” инструментом соуправления лагеря (не просто каталогом).

## 3) Единая прогрессия (что и когда открывается)

Чтобы Loops работали как игра, а не как “меню функций”, нужна прогрессия‑разблокировка:

### 3.1. Мини‑лестница доступа (MVP → post‑MVP)
1) **Traveler**: изучает, пробует, сохраняет локально.
2) **Participant**: ведёт маршруты, фиксирует уровни, делится моментами.
3) **Path Creator**: предлагает значки/категории/арты (UGC).

### 3.2. Гейты для Creator‑ветки
Из `FEATURE_PATH_CREATOR.md`:
- `1.16.1` (Путеводитель) → открыть “Мастерскую” для предложения значков.
- `1.16.2` (Создатель новой категории) → открыть “Архитектора” категорий (или по коду от вожатого).

Практическая привязка к текущему коду:
- статусы уровня уже хранятся по `levelId` (например `1.16.1`, `1.16.2`) в localStorage.
- значит, гейт можно реализовать **без backend**: проверяем `progress['1.16.1']` и `progress['1.16.2']`.

## 4) UX‑склейка: как это выглядит как “единый продукт”

### 4.1. Smart Onboarding (из `ANALYSIS_AND_VISION_2026.md`)
Цель: игрок быстро понимает “паспорт”, “маршруты”, “коллекцию”, “ИИ‑помощь”.

Сильная идея: кнопка “Готов начать?”/CTA на главной ведёт **в Профиль**, где запускается обучение.

Как увязать с Creator‑веткой:
- после открытия гейта (например достигнут `1.16.1`) onboarding показывает новый шаг:
  “Открылась Мастерская — теперь ты можешь улучшать Путеводитель”.

### 4.2. “Share Center” как единая точка в продукте
Чтобы шеринг не выглядел как случайный попап:
- в `ProfileView` нужен блок/таб “Поделиться” (центр),
- а из остальных экранов должны быть только “мягкие” триггеры: “хочешь сделать сторис?”.

### 4.3. Всплывашка на главном экране: превращаем обещание в действие
В тексте главной всплывашки уже обещано: “Фиксируйте достижения. Делитесь… Создавайте команды…”.

Продуктовая склейка:
- добавить 1–2 CTA рядом с этим абзацем:
  - “Поделиться прогрессом” → ведёт в “Share Center”,
  - “Создать команду/Движок (MVP)” → ведёт в “Командный мем/приглашение”.

## 5) Tech‑склейка: как делать это без backend (и где backend появится позже)

### 5.1. GitHub Pages‑реальность (MVP)
Основная стратегия документов совпадает с реальностью проекта:
- прогресс/профиль — **localStorage**,
- знания/контент — **статические `public/ai-data`**,
- ИИ‑текст/помощь — **Cloudflare endpoint** (через чат),
- модерация UGC — **Telegram‑deeplink** (без автозагрузки файлов).

### 5.2. “Заявка на Канон” как общий транспорт
Классная общая идея из `FEATURE_PATH_CREATOR.md`:
- любое предложение (badge/category/skin) формируется в “заявку”,
- заявка получает share‑карточку,
- заявка улетает в Telegram (модераторам).

Это можно использовать шире:
- “пруф достижения” (уже есть в `ProfileView`) — это тоже “заявка”, просто другого типа.

То есть у вас вырисовывается общий слой: **Submission Pipeline** (MVP: Telegram, Post‑MVP: KV/DB + панель модерации).

### 5.3. Post‑MVP синхронизация прогресса (из `ANALYSIS_AND_VISION_2026.md`)
Идея “слепка/кода” — хорошая как следующий шаг, но её стоит держать как P1/P2:
- в MVP достаточно localStorage + экспорт/импорт,
- потом можно добавить “код‑слепок” (без ПДн: только ник+эмодзи+ID значков).

## 6) План разработки в геймдев‑логике: вертикальные срезы (Vertical Slices)

Чтобы не утонуть, делаем **не “все системы сразу”**, а рабочие срезы end‑to‑end:

### Slice 1 — SocialGenerator MVP (виральность без видео)
Цель: дать “вау, я могу поделиться” без тяжёлого видеорендера.
- Генерация 9:16 и 16:9 карточек для:
  - “Я начал маршрут”,
  - “Я завершил уровень”.
- Шеринг через Web Share API (если доступно) или “скачать PNG + скопировать подпись”.
- AI на первом шаге: **текст/подпись** (через существующий endpoint), фон — шаблон/пак.

### Slice 2 — Smart Hints (единая подсказка вместо разрозненных попапов)
Цель: убрать хрупкость подсказок и превратить онбординг в продукт.
- единый overlay‑контекст,
- первый вход в профиль = 4 шага обучения,
- кнопка “(?)” для повторного запуска.

### Slice 3 — Creator Workshop (черновик, но уже полезный)
Цель: включить endgame‑ветку как “мастерскую”, даже если пока без community‑голосования.
- таб “Мастерская” в профиле (гейт `1.16.1`),
- формы: “предложить значок”, “предложить арт‑скин”,
- “Заявка на Канон” → Telegram + share‑карточка.

### Slice 4 — “Мой арт” (локальные скины)
Цель: сделать механику “Эволюция Артов” хотя бы в персональном виде.
- хранить кастом‑арт в localStorage (маппинг `badgeId → image data/url`),
- `BadgeIcon` умеет показывать “классика / мой арт”,
- на `BadgeView` появляется переключатель.

### Slice 5 — “Выбор сообщества” (только когда будет канал доставки)
Цель: community‑слой без хаоса.
- сезонный “пак скинов” (курируемый вожатыми) как статический JSON+assets,
- позже — лайки/голосование через backend.

## 7) Контроль качества (что считать “хорошим геймдевом” здесь)

### 7.1. Вкусность (Game Feel)
- каждое ключевое действие даёт понятный отклик (анимация/звук/микро‑состояния),
- “путь” ощущается как живой (в профиле есть понятная динамика),
- шеринг — 2 тапа максимум до результата.

### 7.2. Понятность (Clarity)
- onboarding ведёт игрока к “первому маршруту”,
- везде один язык: “значок = маршрут”, “уровень = шаг”.

### 7.3. Безопасность (дети/РФ/ПДн)
- share‑карточки по умолчанию без персональных данных,
- ник — опционально,
- любые “коды/слепки” не содержат ФИО/телефонов.
