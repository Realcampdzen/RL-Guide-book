# План доработки фронтенда (инструкция для агентов)

## Как пользоваться документом (Agent Runbook)

Этот файл — рабочая инструкция для агентной доработки фронтенда. Внутри:

- **Основной план**: чеклисты по направлениям (пункты 1–10).
- **Ключевой техдолг по стилям**: отдельный блок **2.4 Миграция системы стилей (legacy → Bluenest)** — его лучше рассматривать как “главный проект” по качеству и поддерживаемости.
- **Приложения**: исходные тексты аудитов/разборов (в `<details>`), чтобы можно было быстро сверяться с источником, но не засорять основной план.

### Правила работы агента

- **Сначала стабилизация, потом рефакторинг**: не смешивать в одном изменении визуальные правки и архитектурные.
- **Маленькие итерации**: брать 1–2 пункта из чеклиста, доводить до конца, фиксировать результат.
- **Не ломать UI**: любые изменения стилей проверять на ключевых экранах (intro, categories, category, badge, badge-level, about-camp, чат).
- **Не добавлять новую “третью” систему стилей**: цель — довести до единого Bluenest-подхода и убрать legacy.
- **Чистить dev/agent‑телеметрию**: никакого `localhost`/`127.0.0.1` в проде; любые логи — через DEV‑гейты.

### Где что лежит (ориентиры по репо)

- **Точки входа UI**: `src/App.tsx`, `src/main.tsx`
- **Экраны (views)**: `src/views/*`
- **Компоненты**: `src/components/*`
- **Глобальные стили**: `src/styles.css`, `src/desktop-styles.css`, `src/mobile-styles.css`, `src/style-variables.css`, `src/styles/*`
- **Bluenest**: `src/styles/bluenest.css`, `src/components/BlueNestLanding.tsx`, `src/components/BluenestGlobalStyles.tsx`
- **Legacy‑инъекция стилей** (должна уйти): `src/components/AppStyles.tsx`, `src/styles/App.styles.ts`
- **Данные**: `public/*` (в т.ч. JSON/изображения), `ai-data/*`
- **Сборка/Vite**: `vite.config.ts`

### Важно: как у нас устроены фото/ассеты и почему нельзя “ломать пути”

Сейчас ассеты грузятся корректно за счёт сочетания нескольких вещей (и их важно сохранить):

- Vite `base` настроен на поддиректорию: `vite.config.ts` → `base: '/RL-Guide-book/'`.
- В dev есть middleware, который обслуживает запросы, начинающиеся с `/RL-Guide-book/`, из папки `public/` (см. `vite.config.ts`, плагин `rlGuideBookDevPlugin`). Он умеет декодировать URL (в т.ч. кириллицу и двойное кодирование).
- В build все содержимое `public/` копируется в `dist/RL-Guide-book/` (см. `vite.config.ts`, плагин `copyRLGuideBookPlugin`). Поэтому в продакшене все пути вида `/RL-Guide-book/...` должны существовать в `public/...`.

Практическое правило: если в коде есть ссылка на `/RL-Guide-book/что-то` или `${import.meta.env.BASE_URL}что-то`, этот файл должен лежать в `public/` по соответствующему пути. Не переносить изображения в `src/` “просто так” — это может сломать загрузку на GitHub Pages.

#### Типы ассетов в проекте (как сейчас)

- Категории: `src/components/CategoriesGrid.tsx` берет иконки как `${import.meta.env.BASE_URL}category_${id}.png?v=2` → файлы `public/category_1.png`, `public/category_2.png`, ...
- Аватар/прочие единичные картинки: встречаются прямые пути вида `/RL-Guide-book/Валюша.jpg` (т.е. файл должен лежать как `public/Валюша.jpg`; регистр и название важны).
- Данные значков/категорий: `src/hooks/useDataLoader.ts` грузит JSON/MD по путям вида `/RL-Guide-book/ai-data/...` → папка данных должна лежать в `public/ai-data/...` (в т.ч. `public/ai-data/MASTER_INDEX.json`).
- Фото значков/уровней: генератор путей `src/utils/badgeImages.ts` строит URL через `import.meta.env.BASE_URL` и `encodeURIComponent` по сегментам. Ожидаемая структура:
  - `public/Новые значки/<Название категории>/<Название значка>/<номер> <название>.jpg`
  - опционально реализм: `.../<Название значка>/реализм/<номер> <название>.jpg`

Важно: `badgeImages.ts` содержит нормализацию названий (нижний регистр, ё→е, очистка символов) и частичный маппинг папок категорий. Если добавляете категории/меняете структуру папок — сперва свериться с `badgeImages.ts` и при необходимости расширить маппинг, иначе изображения “пропадут”.

#### Проверки, которые помогают не сломать загрузку фото

- После изменений в ассетах/путях запускать: `npm run build:verify` (или `npm run verify-images`) — проверяет, что картинки корректно попали в `dist/RL-Guide-book/...` (`scripts/verify-images-build.mjs`).
- Для нормализации имен файлов/папок картинок значков: `npm run verify-image-names` / `npm run normalize-images` (`scripts/normalize-badge-images.mjs`).

#### Осторожно с “улучшениями” в путях

- Не менять `vite.config.ts: base` без одновременного аудита всех путей, т.к. часть кода использует `import.meta.env.BASE_URL`, а часть (например, `src/hooks/useDataLoader.ts`) использует абсолютные `/RL-Guide-book/...`.
- Не выкидывать `encodeURIComponent` в генераторе путей изображений значков — он нужен из-за кириллицы в сегментах.
- Не удалять “версии” (`?v=...`) у картинок категорий/домика, пока не понятно, зачем они стоят: сейчас они помогают принудительно обновлять кэш и чинить кейсы с “не перезагрузилась картинка”.
- Если решаем переименовывать ассеты с кириллицы на латиницу — делать это как отдельную задачу: переименование + обновление ссылок + прогон `build:verify`.

### Важно: размеры/адаптивность и “чтобы не сбились размеры”

Основной источник контролируемых размеров сейчас — `src/style-variables.css` (CSS‑переменные для mobile/tablet/desktop). Чтобы не “поплыло”:

- Не хардкодить новые размеры по всему CSS. Если нужно поменять типовые размеры (кнопки, карточки, отступы, шрифты) — сначала смотреть, есть ли переменная в `style-variables.css`, и менять ее.
- Следить за порядком подключения глобальных стилей: `src/styles.css` импортирует `style-variables.css` первым, затем `desktop-styles.css`, затем `mobile-styles.css`. Это обеспечивает стабильную адаптивность.
- Любые точечные inline-стили (например, в `CategoriesGrid.tsx`/`ChatAvatar.tsx`) трогать аккуратно: они часто завязаны на реальный текущий UI и safe-area. Лучше выносить в CSS постепенно и проверять на мобиле.

### Definition of Done (для задач из этого плана)

Считать пункт выполненным, если:

- **Функционально**: фича/рефакторинг работает без регрессий на ключевых экранах.
- **Визуально**: нет “сломанных” слоёв, фонов, скролла, модалок/чата; на мобиле не перекрывается UI.
- **Технически**: нет лишних `console.log`, нет сетевых запросов на `localhost`, нет дублирования переменных/стилей, не добавлена новая конфликтующая система стилей.
- **Проверки**: пройдены `npm run self-check` и `npm run lint` (если эти команды настроены в проекте).

Identified Issues & Pain Points

Through deep analysis of the repository, several issues have emerged that need to be addressed to make the application production-ready. These range from code maintainability problems to potential runtime bugs or UX pitfalls. Below is a comprehensive list of identified pain points:

1. Styling Complexity & Maintainability: The styling approach is currently fragmented and somewhat brittle. There is a massive global CSS string (AppStyles) that defines styles for most components, plus additional CSS files for the new design elements. This has led to heavy use of !important to override conflicts (for example, forcing new z-index rules in BluenestGlobalStyles). Having multiple sources of truth for styles makes it easy for inconsistencies or unwanted side-effects to slip in. It also makes the code harder to maintain – future developers (or AI agents) must remember to update styles in possibly multiple places. In its current state, tweaking a style could have unpredictable results due to the cascade and specificity issues introduced by the overrides. This setup is workable for a prototype, but in production it would be better to consolidate styles (either by fully adopting a single CSS framework or by using a consistent CSS-in-JS solution).

2. Dual “Old vs New” Design Overlap: Related to the above, the project’s UI appears to be transitioning from an older design to a newer one (the “BlueNest” cosmic theme). As a result, some screens use different color schemes and layouts. For instance, the Introduction and Additional Materials modals are treated as needsOldStyles in the code (meaning they perhaps use the original style) whereas the main screens use needsNewStyles. This overlap can lead to inconsistent user experience – e.g., slight differences in font or color between an “old style” popup and the rest of the app – and increases the chance of regression (since one set of styles might inadvertently affect the other). It’s a pain point when trying to ensure a polished, unified look for serious stakeholders. Until this is resolved, developers have to be very cautious about style changes.

3. Cross-Browser Compatibility Gaps: While modern features make the app flashy, some are not universally supported or could break on older browsers:

The hero text highlight uses -webkit-text-stroke with the text color set to transparent. In Chrome and Safari this gives a cool outlined text effect. But in Firefox or any browser that doesn’t support that CSS property, the highlighted word could simply vanish (transparent text with no stroke). There’s no fallback color defined, so this is a real issue on non-WebKit browsers.

The custom cursor and scroll-reveal rely on IntersectionObserver and other modern DOM APIs. Internet Explorer (and some legacy mobile browsers) lack support for IntersectionObserver. Currently, the code does not polyfill it – if IntersectionObserver is not available, the useScrollReveal effect might do nothing (worst case, it could leave elements invisible, since it initially sets their opacity to 0 and only reveals them when observed). That means users on older browsers might never see content appear. Similarly, CSS features like backdrop-filter (used for blurring backgrounds in modals) or CSS variables might not work in very old browsers. The user did mention supporting browsers ~5 years old; around 2018-2019, most features except IE11 were supported, but we should verify critical visual features on, say, Safari 12 or older Android WebView.

There is also extensive use of CSS custom properties and modern syntax (e.g., env(safe-area-inset-top) for notch support). This is great for modern devices, but some older browsers will ignore unknown properties. If not careful, that could degrade the layout. Fortunately, things like ignoring env() just means a bit less padding on old devices, which is not breaking – but it’s worth noting as part of a compatibility audit.

4. Performance Considerations (Initial Load & Effects): The app’s initial load does a lot of work. Fetching ~119 JSON files (even if small) can introduce latency, especially on mobile networks. Although these are done in parallel batches and cached, a slow 3G connection might still struggle, and the user might wait longer than the 1.5s splash screen. Additionally, the multitude of animations and effects can tax older devices:

The custom cursor and magnet effects involve continuous JavaScript (requestAnimationFrame loops to track pointer, collision detection for hover states, etc.). On a low-end mobile device (which won’t use the custom cursor – it’s disabled on touch – but on an older laptop or tablet with pointer, it might cause some jank).

Drop shadows, blurs, and large images: The background images (e.g., the space background and noise overlay) plus heavy CSS shadows on texts and elements can affect rendering performance. For example, each category card image has multiple drop-shadows for the glow effect. On modern GPUs this is fine, but on an older machine it could make scrolling less smooth. Similarly, the Three.js-powered elements (if/when activated) need to be carefully tested on mobile so they don’t overwhelm the device.

Memory usage should also be monitored. Loading all badge data into memory is convenient, but if the badge JSON includes a lot of text (some badges have detailed descriptions, criteria, examples, etc.), the app could be holding a few megabytes of data in JS objects. Not a huge deal for most, but on memory-constrained phones it’s something to watch.

5. Debug/Development Code in Production: Throughout the front-end code, there are console.log statements and even network fetches that appear to be for debugging or analytics during development. For instance, in the category card component, on each click or touch, there’s a fetch to http://127.0.0.1:7242/ingest/... with some debug payload. This looks like an instrumentation or logging mechanism that was used locally (perhaps with an “agent” for testing). In production, such calls are not only unnecessary – they will fail or hang (since that local endpoint won’t exist) – but they also pose a performance issue (unneeded network traffic) and a potential security concern (if any sensitive info were included, which in this case it’s just category IDs and timestamps, but still). All these debug logs and calls need to be stripped out or disabled for a production build. Leaving them in could clutter the browser console for users and even degrade performance slightly. It’s easy to forget such code, so highlighting this as a pain point is important.

6. Accessibility Issues: While the app is not explicitly stated to follow accessibility standards, it’s important if “serious people” (which could include a broad audience) are going to evaluate it. A few concerns:

Some clickable elements are <div> or non-semantic tags (for example, category cards use <div class="card item-card" onClick={...}>). This means they are not focusable via keyboard by default and not announced by screen readers as interactive. Ideally, these should be <button> or <a> elements (with href if navigation) or given tabindex="0" and ARIA roles to be accessible. The team did a good job on the mobile menu and bottom nav by using proper <button> and ARIA attributes, so extending that practice to all interactive elements would be wise.

Color contrast should be reviewed. The design uses neon/cosmic colors on dark backgrounds – visually appealing, but some text (like the faint blue or grey text) might have low contrast. For instance, the badge count text uses a light color #ccc on a dark card, which is probably OK, but any lighter and it could fail contrast checks. Ensuring that important instructional text isn’t in a low-contrast style will help all users, especially in sunlight on mobile.

The custom cursor is disabled for touch (so mobile users get the normal system cursor, which is good). For accessibility, also consider disabling or not using the custom cursor for users who prefer reduced motion or have accessibility settings – a rapidly moving or changing cursor can be distracting. At minimum, it’s fine as is, since on desktop it’s more of a cosmetic enhancement.

Focus management: when the chatbot opens, is focus trapped inside it? When modals (menus, etc.) open, the code does manage some (the mobile menu sets aria-hidden on background and focuses elements correctly, presumably). We should audit that all modals and overlays follow best practices (e.g., pressing Esc closes them – the mobile menu has an event listener for Escape key, which is good).

Overall, accessibility hasn’t been a primary focus in the development so far (understandably, since the priority was functionality), but before a broad launch, it’s something to gradually improve.

7. Incomplete Features / Content: There are a few areas marked as “in development” in the roadmap (integration of chatbot with UI, user progress system, etc.). While these may not be critical for an initial production release, their placeholders should degrade gracefully. For example, if “personalized recommendations” aren’t implemented yet, ensure there’s no dead button or broken link referencing them. If a menu item or section is not ready, consider hiding it in the production version until it’s functional to avoid confusing users. The presence of static HTML pages (bluenest.html, categories.html) in the repo suggests those were interim solutions or prototypes; they likely won’t be used in production (the React app covers their functionality), so any links or references to them (like document.referrer logic in handleBackToIntro) should be cleaned up if not needed. Every visible element in the UI should either do something meaningful or not be shown to end users.

The above points highlight where the repository’s current state might fall short of a seamless, “production-ready” experience. Fortunately, each issue has one or more clear solutions or best practices we can apply.

В App.styles.ts задавались стили скроллбара и др. глобальные вещи. Объединение и оптимизация определения CSS-переменных: В настоящий момент базовые CSS-переменные (цвета, шрифты) объявляются повторно во многих местах. Например, куски с --c-midnight, --c-volt, --f-display и т.д. присутствуют в начале badge-view.css, category-view.css, bluenest.css, возможно, в about-camp.css и других. Такое дублирование затрудняет поддержку – если цвет поменяется, придется менять во всех файлах.

Решение: вынести общие переменные в один файл (вероятно, тот самый style-variables.css). В styles.css уже предусмотрен импорт style-variables.css первым. Нужно заполнить этот файл определениями всех переменных дизайна Bluenest (цветов, шрифтов, easing). Затем во всех остальных CSS удалить дублированные блоки :root { ... }, чтобы переменные брались из единого места.

Замечание: При этом важно, чтобы style-variables.css подключался везде до остальных стилей. Если проект собирается Vite, то импорт через styles.css в index.html уже это делает. Также bluenest.css сейчас повторно определяет переменные (возможно, с той же целью). После рефакторинга bluenest.css можно оставить только reset и глобальные правила, а сами переменные доверить style-variables.css.

Консолидация глобальных стилей нового дизайна: Сейчас имеются некоторые дубли между bluenest.css и другими файлами. Например:

В bluenest.css определены стили для html, body (фон, шрифт), а в category-view.css и badge-view.css задается фон для своих контейнеров .category-view-container, .badge-view-container и т.д., причём тоже с градиентом и картинкой. Нужно убедиться, что фон приложения задается консистентно: либо глобально (через body фон космоса) и локальные контейнеры прозрачные, либо локальные контейнеры имеют фон, а глобальный фон однотонный. Судя по коду, выбран второй подход – каждый экран сам рисует фон (например, .badge-view-container имеет градиент + изображение космоса, .category-view-container – аналогично). Поэтому в BluenestGlobalStyles (или bluenest.css) отключается фон у глобального контейнера .app: там стоит .app { background: transparent !important; }, чтобы не мешать. После удаления старой .app это, возможно, уже не потребуется.

Надо проверить, не противоречат ли друг другу глобальные и локальные стили. Например, в bluenest.css body тоже задает фон (градиент + изображение фоновой звезды), что может конфликтовать с фоном .badge-view-container. Возможно, body фон актуален только для стартового экрана (BlueNestLanding), а при переходе на другие экраны body-фон перекрывается контейнером. Это тонкий момент: следует унифицировать механизм фоновой подложки. Один из вариантов – сделать фон космоса всегда через body/html (как глобальный фон приложения), а внутренние контейнеры иметь прозрачный фон. Или наоборот, как сейчас, body имеет статичный фон, а экраны – свои динамические. Главное, чтобы не было двойного наложения и лишней нагрузки (например, сейчас может отрисовываться два фоновых изображения одновременно: одно из body, другое из контейнера).

Задача: определить источник фонового изображения/градиента для каждого экрана и убрать дубли. Возможно, для BlueNestLanding стоит использовать такой же механизм фонового изображения через контейнер, вместо body. Обратимся к коду: BlueNestLanding рендерит <div className="hero-bg"></div> внутри секции hero, а стили для .hero-bg видимо заданы в bluenest.css: там нет явного .hero-bg, но возможно в импортированном CSS bluenest.css он есть. Надо проверить bluenest.css на наличие .hero-bg. В обрезке не видно, возможно ниже. Скорее всего, bluenest.css содержит .hero-bg { background: url(...) }. Если да, то стартовая страница рисует фон через .hero-bg, а не через body. А body фон мог остаться как рудимент или для fallback.

Итог: устранить противоречия между фоном body и фоном контейнеров, оставить один источник фонового оформления для консистентности.

Внешние стили для компонентов, сейчас имеющих inline-стили: Несмотря на глобальный вынос CSS, некоторые компоненты по-прежнему применяют стили через атрибуты style в JSX. Наиболее явный пример – ChatAvatar (кнопка-аватар открытия чата). В ChatAvatar.tsx практически все оформление кнопки задается через style={{ ... }} пропы прямо в JSX. Там рассчитываются отступы (bottom, right с учетом safe area), размеры и эффекты наведения программно.

Почему это плохо: Такие стили сложнее переопределять и поддерживать, они не пользуются CSS-переменными или медиазапросами (JS вычисляет размер исходя из window.innerWidth), плюс значительная часть стилей статична (цвета, тени), но все равно зашита в коде.

Решение: Вынести оформление ChatAvatar в CSS-класс. Например, можно сделать CSS-класс .chat-avatar-button для самого <button> (часть стилей уже задается через className, но он в CSS, судя по всему, не определен, т.к. ChatAvatar не импортирует свой CSS). Статические стили (фон прозрачный, рамка, курсор, display:flex и т.д.) задать в CSS-файле (например, chat-avatar.css). Динамические параметры (размер, позиция) можно управлять через CSS-переменные или разные классы для мобильного/десктопа. Например, можно на <button> навешивать класс mobile при isMobile, или использовать медиа-запросы CSS для .chat-avatar-button. Расчет Safe Area (отступы для viewport.offsetTop/Left) сложнее учесть в чистом CSS – возможно, небольшая часть стилей останется inline (скажем, style={{ bottom: baseBottom, right: buttonRight }} может остаться), но все декорации (градиентная обводка, тени, масштаб при hover) лучше перенести в CSS, как это сделано для других элементов интерфейса. Например, эффект масштабирования при hover можно сделать через :hover { transform: scale(1.1) } вместо установки через onMouseEnter/onMouseLeave в коде.

Пример для ориентировки: ChatBot (окно чата) уже вынесен в CSS-файл chatbot.css. Стоит проверить, какие классы там определены, возможно, .chat-avatar-button и подобные тоже там есть. Но судя по поиску, chatbot.css скорее содержит стили самого окна чата (контейнер сообщений, инпуты и т.п.). Значит, нужно создать или дополнить CSS для кнопки аватара.

Аналогично, просмотреть другие компоненты на предмет inline-стилей. Например, в BlueNestLanding есть несколько инлайнов: скрытие меню (style={{ display: 'none' }} для .menu-items пока меню не реализовано) и эффект reveal с задержкой (style={{ transitionDelay: '0.2s' }} на заголовке). Эти вещи тоже можно заменить на CSS (например, через добавление класса .reveal-on-scroll JS-утилита уже добавляет нужные эффекты с задержкой, может, inline не нужен). Но это мелочи. Главное – убрать массивные inline-стили, такие как у ChatAvatar.

Проверка подключения и сборки всех CSS в продакшене: После всех изменений необходимо убедиться, что Vite правильно собирает стили. Сейчас стили подключаются двумя способами:

Глобальные (старые) через link в HTML (styles.css импортирует всё).

Новые – зачастую через импорт в компонентах (как import '../styles/category-view.css').

Vite по умолчанию включает такие импорты CSS в бандл. Нужно проверить, не дублируются ли стили или не выпадают ли они: например, bluenest.css импортируется в BlueNestLanding и, вероятно, попадает только когда этот компонент загружен. Но BlueNestLanding используется сразу на старте (intro), так что это ок. Компоненты, загружаемые лениво (React.lazy), такие как ChatBot и ChatAvatar, импортируют CSS внутри себя, Vite должен тоже их учесть при код-сплите.

Тем не менее, возможно, стоит перенести общие стили (bluenest.css, mobile-styles.css и т.п.) в глобальный импорт, чтобы они гарантированно инициализировались. Например, после рефакторинга можно обновить styles.css, импортировав туда bluenest.css и, скажем, mobile-bottom-nav.css (в выдаче был файл для мобильной навигации). Сейчас styles.css импортирует только старые desktop/mobile стили. Вероятно, имеет смысл туда же добавить @import 'bluenest.css'; чтобы гарантировать применение базового reset и курсора с самого начала. Либо убедиться, что BlueNestGlobalStyles (который рендерит <style> с теми же правилами) выполняется сразу. В App.tsx BlueNestGlobalStyles вставляется условно, но после удаления AppStyles и рефакторинга, возможно, этот условный рендер вовсе уйдет, а мы просто подключим все CSS глобально.

Итого: убедиться, что после удаления AppStyles, стили из него не исчезли бесследно. Вероятно, почти всё уже есть в desktop-styles.css и отдельных файлах. Просто проверим, что такие детали, как стили скроллбара, присутствуют где-то. В App.styles.ts задавались стили скроллбара для WebKit и Firefox. В новом CSS я пока не увидел этих правил – стоит перенести их, например, в desktop-styles.css либо в bluenest.css (чтобы продолжали действовать на весь документ). Это мелкий, но заметный нюанс UX.

Очистка от временного и отладочного кода перед продакшеном: Помимо стилей, обратить внимание на участки кода, которые не должны попасть в продакшен:

Логи и отладочные вызовы: В некоторых компонентах есть console.log и даже вызовы fetch к локальному адресу 127.0.0.1:7242/ingest для логирования пользовательских действий (видимо, debug telemetry). Например, в BlueNestLanding при клике по кнопке чата выводится лог, в CategoriesGrid при клике/hover по категории – fetch('http://127.0.0.1:7242/ingest/...') с отладочными данными, и много подобных блоков (помечены // #region agent log). Эти вызовы явно для разработки и отладки AI-агента. Их нужно отключить или удалить в продакшн-сборке, иначе приложение будет пытаться стучаться по несуществующему адресу и засорять консоль. Как минимум, удалить console.log и console.error вызовы, связанные с отладкой, и закомментировать/удалить блоки telemetry (или обернуть их в условие if (import.meta.env.DEV) чтобы не выполнялись в production).

Мертвый код и заглушки: Например, в BlueNestLanding есть меню навигации, которое скрыто (<ul className="menu-items" style={{ display: 'none' }}>) – стоит или реализовать меню, или удалить этот неиспользуемый фрагмент, чтобы не было висячего кода. Также проверить, нужны ли placeholders вроде NEUROVALUSHA кнопки (в коде кнопка с этим текстом открывает чат) – возможно, стоит переименовать на более понятное или локализовать.

Статические ресурсы: Убедиться, что ссылки на изображения корректны. В коде используются пути типа src="/RL-Guide-book/Валюша.jpg" или с BASE_URL (например, category_X.png?v=2). В продакшене (на GitHub Pages/Cloudflare Pages) BASE_URL, вероятно, равен /RL-Guide-book/, так что пути будут правильные. Надо проследить, чтобы все используемые изображения действительно лежат в public/ (судя по именам, да). Неплохо бы проверить, нет ли русских символов в именах файлов, что может вызывать проблемы – например, "Валюша.jpg" содержит кириллицу, в URL это будет кодировано. Лучше переименовать файлы на латиницу во избежание потенциальных ошибок в разных средах (но это больше рекомендация).
