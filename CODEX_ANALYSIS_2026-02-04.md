## 2) Что находится в репозитории (как оно реально работает)

### 2.1. Фронтенд (Vite + React + TS)

Ключевые файлы/узлы:
- `src/app/useAppController.ts` — “контроллер приложения”: deep‑links, scroll restoration, window‑хуки, навигация и часть интеграций (Telegram/материалы).
- `src/hooks/useDataLoader.ts` — **ленивая загрузка данных** из `public/ai-data/*` по фиксированному пути `/RL-Guide-book/ai-data/...` + кэширование (см. ниже).
- `src/hooks/useNavigation.ts` — состояние экранов (`intro/categories/category/badge/badge-level/about-camp/profile/...`) и логика “назад”.
- `src/components/BlueNestLanding.tsx` — главный экран (интро) + **всплывашка “О концепции игры”** + чат.
- `src/views/CategoryView.tsx`, `src/views/BadgeView.tsx`, `src/views/BadgeLevelView.tsx` — основной игровой цикл: категория → значок → уровень.
- `src/views/ProfileView.tsx` — “личный кабинет”: профиль, статистика, маршруты, избранное, экспорт/импорт, “подтверждение значка” через Telegram‑deeplink.

Отдельно важно про base path:
- `vite.config.ts` выставляет `base: '/RL-Guide-book/'`.
- В dev‑режиме есть middleware‑плагин, который **сервит файлы из `public/` по пути `/RL-Guide-book/...`** (важно для кириллицы в путях и соответствия GH Pages).

### 2.2. Данные (ai-data)

Рантайм‑данные для UI читаются из `public/ai-data/*`:
- `public/ai-data/MASTER_INDEX.json`
- `public/ai-data/category-*/index.json`
- `public/ai-data/category-*/introduction.md`
- `public/ai-data/category-*/N.X.json`

Загрузка в UI:
- `src/hooks/useDataLoader.ts` использует **жёстко заданные URL** вида:
  - `/RL-Guide-book/ai-data/MASTER_INDEX.json`
  - `/RL-Guide-book/ai-data/category-<id>/introduction.md`
  - `/RL-Guide-book/ai-data/<path>index.json`
  - `/RL-Guide-book/ai-data/<path><badgeId>.json`

Кэш данных:
- `src/utils/dataCache.ts` хранит **кэш ai‑данных в `sessionStorage`** (`rl-guide-ai-data-cache`).  
  Это ускоряет навигацию “внутри сессии”, но **сбрасывается при закрытии вкладки/браузера** (в отличие от прогресса).

### 2.3. Игровой слой: прогресс, избранное, “доказательства”

#### Прогресс/профиль (localStorage)
Есть контекст прогресса:
- `src/context/ProgressContext.tsx` (hook‑обёртка: `src/hooks/useUserProgress.ts`)

Что хранится:
- `localStorage` ключ: `rl_guide_progress_v1`
- сущности: `profile`, `progress` (map по `BadgeLevelId`), `favorites`, `meta`
- есть `exportData()` и `importData(file)` (JSON‑бэкап)

Что важно продуктово:
- **Прогресс сохраняется между перезапусками** (localStorage), но **строго в рамках одного origin** (домен + порт).
  - Поэтому, если вы переключаетесь между `localhost:3001` ↔ `localhost:3002` ↔ “какой‑то `3005`”, то прогресс *будет “как будто сбрасываться”* — это разные хранилища.
- В `ProgressContext.tsx` сейчас включён `IS_TEST_MODE = true` и проставляются дефолтные достижения (`TEST_DEFAULT_ACHIEVED_LEVELS`). Для клиентов это почти наверняка надо выключить.

#### Где прогресс уже интегрирован в UI
- `src/views/BadgeView.tsx`: кнопка “В путь” вызывает `startRoute(...)` (ставит `in_progress`).
- `src/views/BadgeLevelView.tsx`: отметка выполнения вызывает `updateLevelStatus(..., 'achieved', reflection)` + конфетти.
- `src/views/CategoryView.tsx`: в карточки значков прокидывается `progress` (агрегация по базовому `N.X`).
- `src/views/ProfileView.tsx`: маршруты/избранное/статы/экспорт/импорт.

#### “Подтверждение значка” и файлы
В `src/views/ProfileView.tsx` есть модалка подтверждения (“proof”), которая:
- собирает текст (комментарий/чему научился/влияние/ссылка),
- позволяет выбрать файлы (фото/селфи/документ/файл),
- **но в итоге отправляет в Telegram только текст** (через `t.me/...?...text=`); файлы не прикрепляются автоматически (и это норм для MVP без backend).

Это уже сильный задел под “вирусный контент”: из тех же данных можно строить **share‑карточки**.

### 2.4. Чат‑бот / AI

UI‑компонент:
- `src/components/ChatBot.tsx`

Режимы работы:
- Dev: `POST /api/chat` (через Vite proxy на локальный backend)
- Prod: Cloudflare endpoint `https://real-vibe-ai-studio.pages.dev/api/putevoditel/chat`

Контекст, который UI передаёт в чат:
- `current_view`, `current_category`, `current_badge`, `current_level`, `current_level_badge_title`

Важно: это уже готовый канал “AI‑контента” для шеринга (хотя бы подпись/слоган/микро‑история).

## 3) Staging / сервера / деплой (как устроено сейчас)

### 3.1. Реальные команды и порты (по коду)

Frontend:
- `npm run dev` → Vite на **3001** (`package.json`, `vite.config.ts`)
- `npm run dev:staging` → Vite на **3002** (сейчас это просто другой порт)

Backend:
- `cd backend && python app.py` → Flask на **4000** (внутри `backend/app.py` `app.run(..., port=4000)`)

Preview:
- `npm run preview:prod` → node server **4002** (`server-preview.js`), отдаёт `dist/` с base path `/RL-Guide-book/`

### 3.2. Почему “staging” = “dev”

Ключевой момент: в `vite.config.ts` выставлен `base: '/RL-Guide-book/'`, и dev‑middleware специально делает так, чтобы:
- локально можно было открывать `http://localhost:3001/RL-Guide-book/`,
- и при этом пути к статике совпадали с GitHub Pages.

Это и есть “локальный staging”: вы тестируете ровно то, что будет на GH Pages, включая base path и кириллицу в путях.

### 3.3. GitHub Pages

Workflow:
- `.github/workflows/deploy-simple.yml` — на push в `main` собирает `dist/` и деплоит в Pages.

### 3.4. Нестыковки/дрейф документации (важно привести в порядок)

В репозитории есть дрейф портов/веток:
- `backend/app.py` реально **4000**, но в репозитории ещё встречаются упоминания **5000** в старых доках/скриптах (нужно подчистить).
- `.github/workflows/ci.yml` триггерится на `master/develop`, а деплой — на `main`.

Это не “баги продукта”, но это ломает onboarding и создаёт ощущение хаоса (“где staging?”, “где какой сервер?”).

### 3.5. Про порт 3005

Факт: **`3005` не задан как дефолтный порт** в конфиге/скриптах (Vite dev = 3001), но используется как изолированный режим разработки (см. `DEV_ISOLATED_GUIDE.md`).

На практике это обычно означает одно из трёх:
1) У вас локально запущен фронтенд с оверрайдом порта (`vite --port 3005`), чтобы не конфликтовать с другими сервисами.
2) У вас есть *внешний* dev‑сервер/прокси, который проксирует на 3001/3002, но слушает 3005.
3) Это “память/путаница” с `3002` (dev:staging) или с backend‑портами.

Если вам принципиально нужен `3005` как “официальный сервер фичи мобильной игры”, то самый простой шаг — добавить отдельный npm‑скрипт (например `dev:game`) и использовать его как единый вход.

## 5) Как привязать шеринг прогресса (MVP без backend) — проектирование механики

### 5.1. Что именно шэрим: “момент” вместо “абстрактного прогресса”

Люди делятся не прогрессом как таблицей, а **историей‑моментом**. У вас идеально ложится на философию “значок = маршрут”.

Предлагаю 4 “момента” (каждый = повод для сторис/поста):
1) **Старт маршрута** (“В путь”) — я выбираю направление.
2) **Добавил в избранное** — я собрал свой “wishlist” маршрутов.
3) **Выполнил уровень** (“achieved”) — я сделал реальное действие.
4) **Итог дня/недели** — короткий “рекап” (максимально вирусный формат).

### 5.2. Где в UI это включать (точки интеграции)

Минимально достаточно 3 мест:
- `BadgeView` после `startRoute(...)` → лёгкий тост “Сделать сторис старта?”
- `BadgeLevelView` после `updateLevelStatus(..., 'achieved')` → модалка “Поделиться достижением” (или кнопка рядом с конфетти).
- `ProfileView` отдельный блок “Поделиться” (центр, где можно собрать карточку вручную).

Дополнительно (как вы и предлагаете):
- на “Добавить в избранное” (`BadgeLevelView` / `ProfileView`) → “Сделать рилс/сторис wishlist”.

### 5.3. Как технически сделать “картинку для соцсетей” на GitHub Pages

Вариант MVP (самый надёжный):
- Генерируем **2 PNG** (9:16 и 16:9) прямо в браузере.
- Шэрим через:
  - Web Share API (`navigator.share`) если доступен,
  - иначе — “Скачать” + “Скопировать текст подписи”.

Как рендерить:
- Отдельный “ShareCard” компонент, который можно отрисовать offscreen и конвертировать в изображение.
- Либо чистый `<canvas>` (самая предсказуемая графика и размеры).

Важные детали для UX:
- Всегда показывать предпросмотр обоих форматов (“Story” и “Wide”).
- Переключатель “Скрыть ник” / “Показывать ник”.
- Никаких персональных данных (телефон/возраст/имена) в карточке по умолчанию.

### 5.4. Как добавить “AI‑контент” не ломая ограничения

Чтобы получить “вирусность” уже сейчас, не обязательно генерировать видео ИИ.

Реалистичный MVP:
1) **AI‑подпись/слоган**: при генерации карточки дернуть уже существующий чат‑эндпоинт (prod Cloudflare), попросить:
   - 1 короткую подпись,
   - 3 варианта хэштегов,
   - 1 вопрос аудитории (для вовлечения).
2) **Предгенерённые AI‑фоны**: хранить в `public/` набор фоновых картинок/плашек и выбирать их:
   - по категории,
   - или рандомом “как коллекцию”.

Это даёт ощущение “ИИ‑контента” и очень дешево в разработке/инфре.

А уже post‑MVP:
- генерация новых фонов на сервере (Cloudflare/другой backend) или в оффлайн‑режиме.

### 5.5. Рилсы (видео) — как не попасть в ловушку “сложно/дорого”

Сделать универсальный MP4 “в браузере” сложно из‑за iOS/кодеков и производительности.

Здравый продуктовый ход:
- MVP: **сторис/пост** (PNG) + “AI‑подпись”.
- Post‑MVP: “рилс‑шаблон” как один из путей:
  1) сервер‑рендер (но нужно оценить лимиты/стоимость),
  2) “анимация в браузере” только там, где поддерживается, с graceful fallback.

## 6) Две дополнительные идеи (в дополнение к вашей идее “скрин/рилс по избранному”)

### Идея 1 — “Карточка‑приглашение в Движок” (социальная механика без аккаунтов)

Проблема, которую решает:
- “Создавайте команды” из всплывашки сейчас ничем не подкреплено.
- В лагере людям проще вступать в действие через **приглашение**.

Как это может работать без backend:
1) Пользователь (вожатый/участник) создаёт “Движок” локально: имя, эмблема, 1–3 значка‑цели.
2) Приложение генерирует **пригласительную карточку** (9:16 + 16:9) + **QR‑код/ссылку** вида:
   - `...?view=badge&badgeId=...` (у вас уже есть deep‑links),
   - + короткий “код движка” в query (даже если он пока не хранится на сервере).
3) Другие сканируют QR → открывается нужный значок/маршрут + кнопка “Добавить в избранное / В путь”.

Почему это усиливает UX:
- превращает “шеринг” из “смотрите на меня” в “пойдём вместе”.
- идеально ложится на лагерную оффлайн‑социальность.

### Идея 2 — “Капсула опыта” (рефлексия → автогенерация сторис)

Проблема:
- Чтобы философия “опыт важнее награды” не потерялась, нужно фиксировать **смысл**, а не только чекбокс.

Как:
1) После `achieved` показывать 1–2 микро‑вопроса (очень коротко):
   - “Что ты сделал(а)?” (1 фраза)
   - “Что это изменило?” (1 фраза)
2) Эти ответы (плюс опционально фото) становятся частью “капсулы”.
3) На основе капсулы приложение генерирует **красивую сторис‑карточку**:
   - значок + 2 короткие фразы + дата + аккуратный лейбл “Реальный опыт”.

Почему это работает:
- повышает ценность достижения,
- делает контент “человеческим” (а значит, вирусным),
- поддерживает педагогическую методику (рефлексия).

## 7) Продуктовость “Путеводителя”: дорожная карта по шагам (реалистично)

Ниже — не “идеальный мир”, а путь, который можно делать итерациями, оставаясь в рамках GitHub Pages.

### Шаг A (1–3 дня): привести окружения/доки в единый вид
Цель: чтобы команда и вы сами всегда знали “что запускать”.
- Зафиксировать актуальные порты: фронт `3001`, dev:staging `3002`, backend `4000`, preview `4002`.
- Обновить:
  - `SERVERS.md` (там уже есть основа),
  - батники `start_servers.bat`, `start_all_services.bat`,
  - комментарий в `src/components/ChatBot.tsx` (порт backend).
- Принять решение: нужен ли вообще `dev:staging` как отдельный сценарий или это просто “второй порт”.
- Согласовать ветки в CI (`ci.yml`) vs deploy (`deploy-simple.yml`): `main`/`master`.

### Шаг B (1–5 дней): “не сбрасывался прогресс” как ощущение пользователя
Технически localStorage уже есть, но UX может быть хрупким:
- Выключить `IS_TEST_MODE` для реальных пользователей (или сделать флагом сборки).
- В `ProfileView` сделать заметную кнопку “Сделать резервную копию” (экспорт уже есть) + мини‑пояснение “прогресс хранится в этом устройстве”.
- Для лагеря/клиентов: добавить “QR‑бэкап” (позже) или “отправить себе файл в Telegram”.

### Шаг C (1–2 недели): Share MVP (картинки + подпись)
- Реализовать “Share Center” в `ProfileView`.
- Добавить CTA в всплывашку на главном экране.
- Добавить автопредложение шеринга после:
  - старта маршрута,
  - выполнения уровня,
  - добавления в избранное.

### Шаг D (после MVP): роли/аккаунты/синхронизация
С учётом РФ и детей — лучше идти так:
1) “Гость/путешественник” (без ввода данных) — дефолт.
2) “Код смены/отряда” (псевдоним + код, без ФИО) — лёгкая синхронизация.
3) Родительский режим — только при необходимости и с осознанной политикой данных.

## 8) Юридика/безопасность/чувствительные данные (важно именно для вашего сценария)

Вы прямо обозначили: дети, родители, РФ, соцсети, возможный личный кабинет.

Рекомендации “по умолчанию” для MVP:
- **Никаких персональных данных в share‑карточке** (имя ребёнка, телефон, возраст, отряд, геолокация и т.п.).
- Никнейм — опционально, с тумблером “скрыть”.
- Данные прогресса — локально (как сейчас), плюс экспорт/импорт.
- Регистрационная форма (Telegram) — добавить явный текст:
  - что будет открыто приложение Telegram,
  - что пользователь сам отправляет сообщение,
  - что не стоит указывать лишнее.

Если уходите в аккаунты/синхронизацию:
- минимизация данных (data minimization),
- отдельные роли и ограничения,
- хранение и обработка — только после отдельного решения, где и как вы это делаете (и какие юрисдикции/провайдеры).
