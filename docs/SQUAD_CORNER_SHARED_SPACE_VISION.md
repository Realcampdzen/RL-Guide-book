# Отрядный уголок → общее пространство отряда (видение и план)

Документ описывает, как превратить заполнение данных отряда Вожатым/Разработчиком в **общий кабинет отряда**: пространство с участниками и общими данными/планами, связанное с Движками, значками и Советом лагеря.

---

## 1. Идея

- **Сейчас:** данные «Отрядный уголок» (название, девиз, кричалки, фото, планёрка, значки на флаг) хранятся только локально у каждого пользователя (`userData.diaryProgress.squad` → localStorage). Вожатый заполняет у себя — участники не видят; у участников свои копии.
- **Цель:** при заполнении данных отряда Вожатым/Разработчиком создаётся **общее пространство отряда** (общий кабинет), куда можно добавлять участников или куда участники вступают по коду/ссылке; все видят одни и те же данные и планы. Это пространство связывается с остальным функционалом ЛК: Движки, предложенные значки от отряда/движков, Совет лагеря — единая экосистема.

---

## 2. Что уже есть (ресурсы)

### 2.1. Бэкенд (Vercel backend, Flask, файловое хранение)

| Сущность | Файл/API | Что хранится |
|----------|----------|--------------|
| **Смены** | `shifts.json`, GET/POST `/api/shifts` | id, name, startDate, endDate |
| **Отряды смены** | там же, GET/POST `/api/shifts/<id>/squads` | id, shiftId, name, createdAt, createdBy |
| **Участники отряда** | `memberships.json`, POST `/api/squads/<id>/join`, GET `/api/squads/mine` | deviceId, campId, squadId, role, joinedAt; ответ «mine» — membership + squad + shift + **participants** |
| **Заявки на значки** | уже привязаны к campId/squadId | Вожатый видит заявки по своему отряду (inbox по squadId) |
| **Движки (Teams)** | отдельный API | создание/вступление/состав, данные команды (название, девиз, логотип и т.д.) — **образец «общего пространства с участниками»** |

То есть уже есть:

- создание смен и отрядов (руководитель смены/разработчик);
- выдача кодов (participant/counselor, привязка к смене);
- вступление в отряд по squadId (participant получает membership);
- список участников отряда (GET `/api/squads/mine` → participants).

**Чего нет:** у отряда смены нет «контента» — названия, девиза, фото, планёрки и т.д. на бэкенде. Сейчас это только в фронте в `diaryProgress.squad` у каждого пользователя.

### 2.2. Фронтенд

- **Отрядный уголок:** `SquadCornerDashboard` — табы Отряд / Фото / Планёрка / Значки на флаг; «Сохранить отряд» → `updateDiarySquad(...)` → только локальный стейт и localStorage.
- **Участник в отряде:** есть вызов `loadMySquad(accessToken)` (badgeApprovalApi), в ProfileView есть логика «Мой отряд» (вступление по squadId, статус). То есть «я в отряде» и список участников уже можно получить.
- **Движки:** полный цикл — создание, вступление, общие данные на бэкенде, отображение в ЛК. Можно использовать как образец для «общего кабинета отряда».

## 3. Что нужно сделать (логически)

### 3.1. Общее пространство отряда (squad space)

1. **Хранить контент отрядного уголка на бэкенде по отряду смены.**
   - Либо расширить объект отряда в `shifts.json` (поле, например, `payload` или `squadCorner`), либо отдельный store (например, `squad_data.json`: ключ — squadId, значение — объект как сейчас `diaryProgress.squad`: name, motto, chants, greeting, memes, photoCorner, photoFlag, photoSquad, photoWithCounselors, planGridA, planGridB, flagBadgeRequests, flagBadgesApproved).
   - Учитывать размер (фото в base64): лимит размера или вынос фото в отдельное хранилище позже.

2. **API для чтения/записи этого контента.**
   - `GET /api/squads/<squadId>` — мета (name, shiftId) + контент уголка (для участников отряда или для всех по смене — решить политику).
   - `PATCH /api/squads/<squadId>` — обновление контента уголка. Право: только тот, кто в отряде с ролью counselor, или shift_leader этой смены (или отдельная роль «редактор уголка»).

3. **Фронт.**
   - Если у пользователя есть membership в отряде (GET `/api/squads/mine` возвращает squad):
     - при открытии «Отрядный уголок» загружать контент с GET `/api/squads/<squadId>` и показывать его как общий;
     - для вожатого/редактора: «Сохранить отряд» → PATCH `/api/squads/<squadId>` с текущими полями; затем обновить локальный кэш/стейт.
   - Если пользователь не в отряде — оставить текущее поведение (локальный уголок в `diaryProgress.squad`), либо показать «Вступите в отряд по коду, чтобы видеть общий уголок».

4. **Участники.**
   - Добавление участников уже есть: выдача кода (participant + shiftId) и вступление по коду; после вступления участник получает squadId (через выбор отряда или логику «один отряд на смену» — при необходимости доработать). Вступив, участник видит общий уголок по GET `/api/squads/<squadId>`.

### 3.2. Связь с Движками, значками, Советом

- **Движки:** сейчас Движок — отдельная сущность (команда по интересам). Связка «отряд смены ↔ Движок»: например, поле у отряда `teamId` (опционально) или у Team `squadId`. Тогда в интерфейсе «Отрядный уголок» можно показывать «Движок вашего отряда» и наоборот — в Движке «Отряд смены», если привязан. Реализация — после появления общего пространства отряда.
- **Значки:** заявки на значки уже привязаны к squadId; в общем уголке блок «Значки на флаг» может показывать общий статус (кто подал, кто утверждён) при наличии API/данных.
- **Совет лагеря:** инициативы могут ссылаться на смену/отряд; обзор решений по лагерю уже есть, связь с Движками — через useTeam; при появлении squad↔team связи Совет сможет опираться и на отряд.

Эти связи лучше вводить по шагам: сначала общее пространство отряда, потом опциональная привязка Движка к отряду, затем уточнение значков и Совета.

## 4. Пошаговый план (с учётом ресурсов)

### Фаза 1: Контент отряда на бэкенде (минимум)

- **Бэкенд:** ввести хранилище контента уголка по squadId (расширить squads в `shifts.json` полем `squadCorner` или отдельный файл с большими payload). API: GET и PATCH `/api/squads/<squadId>/corner` (или GET/PATCH `/api/squads/<squadId>` с полем body для уголка). Права: чтение — участник отряда (или по membership); запись — counselor этого отряда или shift_leader смены.
- **Фронт:** при открытии «Отрядный уголок» и наличии `mySquad` (из GET `/api/squads/mine`) загружать контент с бэкенда и показывать его; кнопка «Сохранить отряд» для вожатого/редактора отправляет PATCH с текущими полями. Локальный `diaryProgress.squad` использовать как черновик до вступления в отряд или как fallback при офлайне (по желанию продукта).

**Результат:** вожатый заполняет уголок и нажимает «Сохранить отряд» → данные попадают в общее пространство отряда; участники, вступившие в отряд, видят те же данные.

### Фаза 2: Вступление и «общий кабинет»

- Убедиться, что участник после вступления по коду однозначно попадает в отряд (squadId в membership). При необходимости — доработать выдачу кода (привязка к отряду) или выбор отряда при входе в смену.
- В UI «Отрядный уголок» для участника: заголовок «Общий уголок отряда [название]», список участников (уже есть в ответе `/api/squads/mine`), только чтение или ограниченное редактирование по роли.

### Фаза 3: Связи с Движками и остальным

- Опциональная связь отряд ↔ Движок (поле squadId у Team или teamId у squad) и отображение в ЛК («Движок отряда» / «Отряд смены»).
- Использование squadId в заявках на значки и в Совете лагеря — уже частично есть; при необходимости расширить отображение и фильтры.

---

## 5. Ресурсы и ограничения

- **Бэкенд:** текущий Flask-API и файловое хранение (shifts, memberships) достаточны для Фазы 1–2. Большие payload (фото в base64) могут потребовать лимита размера или выноса в хранилище (позже).
- **Фронт:** один разработчик/небольшая команда может реализовать Фазу 1 за несколько дней: бэкенд — хранилище + GET/PATCH; фронт — проверка mySquad, загрузка уголка, «Сохранить» → PATCH.
- **Роли:** уже есть participant, counselor, shift_leader; право «редактировать уголок» можно привязать к counselor в этом отряде и shift_leader смены.

Итого: идея «при заполнении данных отряда создаётся общий кабинет отряда, куда можно добавлять участников и где все видят общие данные» реализуема на текущем стеке; ключевой шаг — вынести контент отрядного уголка на бэкенд и связать его с существующими сущностями «смена → отряд → участники».
