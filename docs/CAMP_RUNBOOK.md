# CAMP_RUNBOOK — как провести смену с “Путеводителем” (pilot)

**Срез:** 2026‑02‑21  
**Назначение:** пошаговая инструкция для staff “как это реально использовать на смене” (онбординг, ежедневная работа, инциденты, финиш).

Связанные документы:
- SSOT: [`docs/PRODUCT_MECHANICS_AND_ROADMAP.md`](PRODUCT_MECHANICS_AND_ROADMAP.md)
- Playbook релиза: [`docs/PROD_RELEASE_PLAYBOOK.md`](PROD_RELEASE_PLAYBOOK.md)

---

## 1) Роли и ответственность (pilot)

- **shift_leader (старший вожатый / руководитель смены)**
  - создаёт смену и отряды
  - организует онбординг детей (unlock по коду)
  - помогает вожатым с доступами и модерацией
- **counselor (вожатый)**
  - кабинет отряда: участники, приглашения, исключение, чат
  - уголок отряда: айдентика, фото, планёрка
  - заявки на значки: поддержка детей (а не только “проверка”)
- **participant (ребёнок)**
  - личный прогресс: “В путь”, дневник, инспектор, заявки
  - вступление в отряд и участие в чате/кабинете
- **parent (родитель)**
  - read‑only витрина прогресса ребёнка по `parent_code/QR` (без управления)

---

## 2) Старт смены (T‑0)

### 2.1. Проверить стенд
1. Открывается фронт (Vercel/стейдж/локально).
2. Backend отвечает `GET /api/health`.
3. Есть персистентность (для пилота: Supabase, в dev допустим JSON).

### 2.2. Создать смену и отряды
1. Войти как `shift_leader`.
2. Открыть таб **“Смены и отряды”**.
3. Создать смену (если ещё не создана).
4. Внутри смены создать нужные отряды.
5. Для каждого отряда подготовить инвайт‑код (или ссылку).

### 2.3. Сверить “кто за что отвечает”
- Кто отвечает за онбординг детей по кодам.
- Кто модерирует заявки на значки (обычно вожатые, старший вожатый как эскалация).
- Кто отвечает за инциденты (ошибки 401/403/500, спам в чатах).

---

## 3) Онбординг участника (deviceId → код → JWT)

**Цель:** выдать ребёнку доступ к “дорогим” online‑фичам (чат/отряд/модерация) через unlock по коду.

### 3.1. Что делает участник
1. Открывает ЛК (кабина).
2. Находит bubble “Код / Войти по коду” (sandbox/utility).
3. Получает (или показывает staff) свой идентификатор устройства (`deviceId`) и вводит выданный код (unlock).

### 3.2. Что делает staff
1. Получает от ребёнка `deviceId`.
2. Генерирует код в staff‑интерфейсе (органайзер/служебная панель).
3. Передаёт код ребёнку, ребёнок вводит код и получает JWT.

**Если код не подходит / истёк:**
- сгенерировать новый
- убедиться, что ребёнок вводит код на том же устройстве/браузере

---

## 4) Вступление в отряд и проверка кабинета

### 4.1. Вступление по коду
1. Участник открывает **“Смены и отряды”** → блок “Мой отряд”.
2. Вводит invite‑код отряда → preview → confirm → join.
3. После join открывает **“Отрядный уголок”** → таб “Отряд” = кабинет.

### 4.2. Вступление по ссылке
1. Участник открывает ссылку `?join_squad=<squadId>`.
2. Видит preview → confirm → join.
3. После join открывается кабинет через “Отрядный уголок”.

### 4.3. Если вступил “не туда”
- Выйти из отряда (leave) и вступить в правильный.
- Важно: membership **одно на устройство**, вступление в другой отряд заменяет текущий.

## 5) Ежедневная работа на смене

### 5.1. Кабинет отряда (участники/чат/инвайты)
У вожатого:
- выдавать invite‑коды/ссылки
- исключать (kick) при необходимости (ошибка/спам/перевод)

У участника:
- видеть состав отряда
- чат отряда (общение + организационные сообщения)

### 5.2. Отрядный уголок (атрибутика/фото/планёрка)
- Редактирует staff (в первую очередь `counselor`).
- Участник потребляет инфо через кабинет (read‑only).

Рекомендованный минимальный цикл:
1. Название + 1 фото (чтобы кабинет “открывался” и был базовый аватар).
2. Флаг/девиз/планёрка — по мере готовности.

### 5.3. Значки: заявки и подтверждения
Участник:
- выбирает цель (“В путь”)
- выполняет и отправляет заявку (пруф)
- синхронизирует подтверждения и видит achieved

Staff:
- открывает inbox заявок
- approve/reject + короткий комментарий
- помогает ребёнку “переоформить доказательство”, если оно слабое/неэтичное/небезопасное

### 5.4. Родители
Staff/ребёнок:
- создаёт `parent_code/QR` (витрина прогресса)
- передаёт родителю (в чате/бумаге/встреча)

Родитель:
- открывает read‑only отчёт

---

## 6) Инциденты и поддержка

### 6.1. 401 (сессия истекла)
- повторить unlock по коду
- проверить, что роль/токен соответствует текущей задаче

### 6.2. 403 (нет прав)
- проверить роль (participant vs counselor vs shift_leader)
- проверить membership (в каком отряде устройство)

### 6.3. 500 (ошибка сервера)
- проверить backend health
- проверить DB доступность (Supabase)
- собрать минимальный репорт: кто/какая роль/какое действие/скриншот/время

### 6.4. Спам/абьюз в чате
- kick/leave при необходимости
- включить/усилить лимиты
- запрет ссылок / фильтр (политика safety)

---

## 7) Финиш смены (T‑end)

1. Экспорт прогресса (у детей/вожатых, если требуется по методике).
2. Сформировать отчёты для родителей (parent snapshots) при необходимости.
3. Решить политику хранения:
   - сколько хранить чаты/уголки/заявки
   - когда удалять смену (админ‑действие)
4. Для dev/test окружений: очистить тестовые сущности (shift/squad delete) аккуратно, чтобы не потерять данные реальной смены.
