# 🚀 Воркфлоу: Безопасный распил монолитных React-компонентов

Этот воркфлоу гарантирует максимальное качество, страхует от утечек состояния (state leaks), "тихих" рендеров и потери пропсов. Он разработан специально для сложной архитектуры экосистемы Путеводителя ("Реальный Лагерь"), где тесно переплетены Three.js, аутентификация и стейт-менеджмент прогресса.

## 🔎 Этап 1: Радары и Карантин (Discovery & Dependency Mapping)
**Задача:** Избежать "слепого" вырезания кода, которое ломает связи и контексты.
1. Запуск `npm run type-check` (или `npx tsc --noEmit`) для фиксации "нулевой точки". Убеждаемся, что до наших действий ошибок нет (или логгируем их базовый уровень).
2. Выбор **одной** логической единицы за итерацию (например, "Модалка Инспектора").
3. Составление **Реестра Зависимостей**:
   - Какие `useState` используются внутри этого куска?
   - Какие значения из контекстов (`useAuth`, `useUserProgress`, `useTeam`) нам нужны?
   - Вызывает ли этот кусок `useEffect`, который опирается на стейт компонента-родителя?

## 🏗️ Этап 2: Подготовка Строительных Лесов (Tactical Scaffolding)
**Задача:** Создать жесткие контракты (интерфейсы) для прослойки между новым компонентом и монолитом.
1. Создаём отдельную папку или заголовок файла (например, `src/views/profile/components/InspectorModal.tsx`).
2. Пишем **строго типизированный `interface Props`**:
   - Никаких `any`. Все `onSubmit`, `onClose` и флаги состояния должны быть явно типизированы.
   - Если передаётся более 3-4 функций, рассмотреть оборачивание их в единый объект `handlers` или использование существующих контекстов напрямую внутри нового компонента (если компонент достаточно изолирован).

## 🪚 Этап 3: Ювелирная Резекция (Component Slicing)
**Задача:** Физический перенос логики. Делается строго по одному компоненту (Single-Piece Flow).
1. Копируем целевой JSX в новый компонент.
2. Подключаем все недостающие импорты (ошибки линтера подскажут, что забыли).
3. Инкапсулируем локальный стейт: если `useState` используется *только* в этой модалке (например, локальный инпут текста), этот `useState` должен "переехать" вместе с компонентом из монолита.
4. Вызов `useContext` внутри нового компонента: если компонент глубоко привязан к `useUserProgress`, лучше вызвать хук внутри него, чем пробрасывать плотно загруженные данные (user data) через 10 слоев пропсов из `ProfileView.tsx`.
5. Замена вырезанного куска в основном монолите `<InspectorModal open={show} ... />`.

## 🛡️ Этап 4: Эшелон Защиты и Сверки (Regressive Validation)
**Задача:** Удостовериться, что изменения невидимы для конечного пользователя, кроме ускорения работы.
1. Сразу же запускаем `npx tsc --noEmit`. TypeScript выявит 99% опечаток, "потерянных" props и нестыковок типов.
2. Проверка Linter: `npm run lint`.
3. Запуск локального сервера (через `npm run dev` или `start_all_services.bat`), если доступен браузер:
   - Открыть перенесённый компонент.
   - Прокликать кнопки "Сохранить", "Закрыть".
   - Убедиться, что Overlay (затемнение) не ломает событие onClick под ним.
4. **Обязательный Коммит (Checkpoint)**: `git add . && git commit -m "refactor: extracted InspectorModal from ProfileView"`.
   - Ветка (Branching): если это крупная фаза, выносить изменения в ветку `refactor/profile-view`.

> [!WARNING]
> Если на Этапе 4 получено более 3 непредвиденных багов — **сделать откат на предыдущий коммит**. Дебаггинг сломанных абстракций обходится дороже, чем повторный, более аккуратный перенос.

## 🚀 Этап 5: Оптимизация (Memoization) (Опционально)
**Задача:** Сделать так, чтобы монолит не рендерил дочерние компоненты понапрасну.
1. Оборачиваем новый компонент в `React.memo()`, если его пропсы стабильны.
2. Экстрактируем тяжелые функции в родительском монолите в `useCallback()`, чтобы не рвать мемоизацию при каждом рендере.

## 🔁 Итерационный цикл
Возврат к Этапу 1. Этот цикл повторяется для:
1. Модальных окон (Child Route, Confirmations).
2. "Катушек" и больших секций (Движки, БРО).
3. Навигации и шапок.
4. Стейт-контроллеров (вынос оставшейся бизнес-логики в кастомные хуки `useProfileState` / `useProfileNavigation`).
