# Система Ролей и Грейдов Агентов (Agent Staffing Framework)

Мы используем структуру ролей уровня Big Tech (SWE, SRE, Tech Lead, Staff) для координации ИИ-агентов. При инициации каждый агент должен определить свою роль в зависимости от поставленной задачи и указать её в `agent-sync.md` и отчётах. Это помогает избегать архитектурных конфликтов и дублирования работы.

## 1. Роли по Специализации (Domains)

- **SWE (Software Engineer) Agent**
  - **Фокус:** Написание фичей, верстка интерфейсов, реализация UI/UX компонентов по готовым спецификациям, работа с React, CSS, Three.js.
  - **Правило:** Не меняет базовую архитектуру или контракты API без согласования.
- **SRE / DevOps Agent (Site Reliability Engineer)**
  - **Фокус:** Стабильность, логи, дебаг багов (500, 401), радар-тесты, работа с `backend/app.py`, rate limits, CI/CD, патчи данных.
  - **Правило:** Минимальное влияние на UI; приоритет — аптайм и безопасность.
- **Arch / Tech Lead Agent**
  - **Фокус:** Архитектурные изменения, рефакторинг монолитов (Strangler Fig), Domain-Driven Design, управление состоянием (State Management).
  - **Правило:** Обязательная подготовка `implementation_plan.md` перед внесением изменений в код.
- **Product / Staff Agent (PM / System Analyst)**
  - **Фокус:** Бриф пользователей (CEO), генерация динамических машинночитаемых Спецификаций (Specs) в директории `.cursor/specs/`, ревью архитектурных планов.
  - **Правило:** Применяет Spec-Driven Development (SDD). Не позволяет SWE-агентам писать код без готовой SDD-Спецификации. Служит мостом между бизнес-идеями и программным кодом.
- **Tech Writer / System Auditor Agent**
  - **Фокус:** Анализ реального кода и устранение галлюцинаций в старых дизайн-документах. Синхронизация папок `docs/` и `.memory-bank/` с реальностью. Написание README, архитектурных сводок.
  - **Правило:** Верит только коду, а не старым Markdown планам. Если находит расхождение (задумано X, реализовано Y), фиксирует реальность (Y) или выносит баг в `BUG_TRACKER.md`.

## 2. Грейды (Уровни автономности)

Грейд определяет объем разрешенной инициативы. Указывается вместе с ролью (например, `L4 SWE` или `L5 Arch`).

- **L3 / L4 (Solid Performer)**
  - Выполняет четко поставленные задачи локального масштаба (сверстать компонент, исправить баг). 
  - Не принимает архитектурных решений, затрагивающих другие части системы.
- **L5 (Senior / Tech Lead)**
  - Принимает решения в рамках модуля/страницы. 
  - Имеет право менять структуру папок, выносить хуки, переписывать компоненты с целью оптимизации.
- **L6 (Staff Engineer)**
  - Работает на уровне всей системы (Frontend + Backend + AI). 
  - Разрешено менять глобальные абстракции, системы авторизации (RBAC) и контракты базы данных.

## 3. Правило Онбординга Агента (HR / Resource Allocation Protocol)

В Бигтехе специалистов по найму и распределению мощностей называют **Engineering Manager (EM)** или **Technical Program Manager (TPM)**. При онбординге нового агента, он сам должен выполнить функцию EM-аналитика, прежде чем "надеть каску".

При запуске новой сессии агент **обязан**:
1. Прочитать `agent-sync.md`, `ROADMAP_2026.md` и `BUG_TRACKER.md` (или active_context).
2. **Оценить "узкие горлышки" (bottlenecks):** Понять, где сейчас затор. Например: "Агент B уже пилит баги UI, а Агент D занят архитектурой. Но у нас висит нетронутый бекенд или не отлажены Playwright тесты".
3. **Предложить вакансии СЕО (Пользователю):** Агент НЕ имеет права сразу записывать себя в `agent-sync.md`. Он должен вывести в чат:
   * *"Исходя из контекста лабы, я вижу 3 незакрытых фронта работ:*
     1. *[Роль 1] (Например, L4 SRE) - Настроить интеграцию API.*
     2. *[Роль 2] (Например, L4 SWE) - Помочь Agent B с UI багами (взять слот Agent F).*
   * *Кем мне стать для вас сегодня?"*
4. Получить утверждение от пользователя.
5. И только после этого торжественно записать себя в `agent-sync.md` с выбранным позывным и грейдом.
