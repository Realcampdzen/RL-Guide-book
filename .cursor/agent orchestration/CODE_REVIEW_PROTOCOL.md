# CODE REVIEW & AUDIT PROTOCOL (Git-Flow для ИИ Агентов)

## Гибридная стратегия разработки
Чтобы соблюсти баланс между скоростью работы ИИ и корпоративной безопасностью (Big Tech), мы используем гибридный процесс слияния кода. Агенты **не имеют права ломать `main`**.

### 🟢 Уровень 1: Мелкие фиксы (Direct to Main)
*Что сюда входит:* Текстовые правки, мелкие исправления CSS, добавление console.log, простые фиксы тривиальных UI багов (до 10 строк кода).
*Процесс:* Агент имеет право вносить правки напрямую в `main` и сразу проверять результат в браузере. Слияние (Review) не требуется.

### 🔴 Уровень 2: Карантин и Код-Ревью (Strict Git-Flow)
*Что сюда входит:* Новая архитектура, рефакторинг монолитов (ProfileView), изменения в `auth`, БД миграции, новый функционал, затрагивающий более одного файла или более 30 строк кода.

*Процесс (Для Агента-Исполнителя):*
1. Создать новую ветку: `git checkout -b feature/<task-name>`
2. Внести изменения в код.
3. Проверить код линтером: `npm run lint`.
4. Закоммитить: `git add . && git commit -m "Умный текст коммита"`.
5. Скопировать `PR_TEMPLATE.md` и создать файл `.cursor/pull_requests/PR_<TASK>.md` со своим отчетом.
6. Вывести текущий diff (рекомендуется командой `git diff main > .cursor/pull_requests/PR_<TASK>.diff`).
7. Вернуться в `main`: `git checkout main`.
8. Обновить свой статус в `agent-sync.md` (Ожидает ревью). Завершить сессию.

*Процесс (Для Агента-Ревьювера из Отдела QA & Security):*
1. Открыть открытые PR в `.cursor/pull_requests/`.
2. Переключиться на ветку `git checkout feature/<task-name>`.
3. Оценить логику, поискать уязвимости безопасности, проверить стандарты кода. Убедиться, что сборка не падает.
4. Вынести вердикт:
   - Если **Reject**: Заполнить комментарии в `PR_<TASK>.md`, вернуть статус в `agent-sync.md`.
   - Если **Approve**: Влить в main `git checkout main && git merge feature/<task-name>`. Удалить ветку и файлы PR (или перенести в `pull_requests/archive/`). Обновить трекер.

## Чего ищет Ревьювер (Checklist)
1. Нет ли здесь хардкода?
2. В безопасности ли Supabase JWT (нет ли утечек ключей)?
3. Соответствует ли дизайн гайдлайнам (Accepted UX)?
4. Избегаем ли мы монолитов (запрещено создавать компоненты > 300 строк)?
